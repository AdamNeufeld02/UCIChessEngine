# Testing workflow

Tools for answering two different questions:

- **A. "Did my change actually help?"** — SPRT self-play via `run_sprt.ps1`, ready now.
- **B. "What are the best values for all these margins/scales/weights?"** — parameter
  tuning, sketched below, intentionally not built yet (see [Part B](#part-b-future-parameter-tuning)).

## What's in here

- `fastchess/fastchess.exe` — match runner (SPRT-aware, faster/actively-maintained
  successor to cutechess-cli). Not committed to git; see [Setup](#setup) to fetch it again.
- `books/8moves_v3.pgn` — ~8000 short varied openings so games aren't all identical
  from `startpos`. Also not committed; see [Setup](#setup).
- `run_sprt.ps1` — builds two engine binaries and runs an SPRT match between them.
- `engines/`, `build/`, `.worktree/`, `results/` — generated by the script, gitignored
  (except `results/.gitkeep`).

## Setup

If `fastchess/fastchess.exe` or `books/8moves_v3.pgn` are missing (fresh clone, or you
deleted them since they're gitignored):

```powershell
# fastchess (pick the release for your OS from the releases page if this version is stale)
Invoke-WebRequest https://github.com/Disservin/fastchess/releases/download/v1.8.2-alpha/fastchess-windows-x86-64.zip -OutFile fastchess\fastchess.zip
Expand-Archive fastchess\fastchess.zip fastchess -Force
Move-Item fastchess\fastchess-windows-x86-64\fastchess.exe fastchess\fastchess.exe -Force

# opening book
Invoke-WebRequest https://github.com/official-stockfish/books/raw/master/8moves_v3.pgn.zip -OutFile books\8moves_v3.pgn.zip
Expand-Archive books\8moves_v3.pgn.zip books -Force
```

## Important prerequisite: commit the MSVC portability fix first

`run_sprt.ps1` builds the **baseline** by checking out a git ref into a throwaway
worktree and compiling it. While setting this up, every ref currently in history —
including `HEAD` — **failed to build under MSVC**: `bitboards.h` has always called
`__builtin_popcountll`/`__builtin_ctzll`/`__builtin_clzll`, which are GCC/Clang
builtins with no MSVC equivalent. Your uncommitted working-tree change (switching to
`std::popcount`/`std::countr_zero`/`std::countl_zero`) is what actually fixes this —
it just isn't committed yet, so no historical commit can serve as an MSVC baseline.

**Commit that portability fix on its own (before any behavior-changing search/eval
work) so `HEAD` becomes a usable baseline.** Until then, pass `-BaselineRef` pointing
at a commit-ish that already contains the fix (e.g. `git stash create`'s output, or a
temporary commit) if you want to test something sooner.

## Part A: verifying a change (ready now)

```powershell
cd testing

# Default: current working tree vs your last commit, "does this gain Elo" bounds
.\run_sprt.ps1

# Compare against something further back
.\run_sprt.ps1 -BaselineRef main~5

# A refactor/speedup that shouldn't change behavior — tighter, "did I break something" bounds
.\run_sprt.ps1 -Bounds nonregression

# Custom bounds, longer time control, explicit concurrency
.\run_sprt.ps1 -Elo0 0 -Elo1 10 -TC "10+0.1" -Concurrency 8
```

What it does:
1. Builds `dev` = your current working tree (uncommitted changes included) with CMake/MSVC Release.
2. Checks out `-BaselineRef` (default `HEAD`) into a scratch worktree and builds it the same way.
3. Runs `fastchess` between the two with the given time control, `1` search thread and
   `16MB` hash each (so `-Concurrency` games run in parallel instead — standard practice,
   keeps games fast and reproducible), the 8-mover opening book (random, both colors per
   opening), and adjudication rules to end lopsided/dead-drawn games early.
4. `fastchess`'s built-in SPRT stops the match once there's enough evidence for or
   against the bounds and prints an LLR trace, Elo estimate, and W/L/D counts.
5. PGN + log for every run land in `results/` with a timestamp, in case you want to
   look at specific games afterward.

**Reading the result:** LLR crossing the upper bound = accept (the change gained Elo
within your bounds); crossing the lower bound = reject (it didn't, or lost Elo). If
it's inconclusive after a very long run, the true Elo delta is likely close to your
bounds — pick tighter bounds or just accept "no detectable difference at this budget."

**Choosing bounds:** `normal` (`[0, 5]`) is the right default for "is this a real
improvement" questions — most single features/tweaks either clearly clear this or
clearly don't. `nonregression` (`[-3, 1]`) is for changes that shouldn't affect
strength at all (refactors, speed-ups, code cleanup) — it confirms you didn't
accidentally regress. For search-parameter tuning results you're validating one at a
time, `normal` bounds with more rounds is usually the better default over
`nonregression`.

**Time control:** `8+0.08` (STC-ish) is fine for a quick first read; bump to something
like `10+0.1` or `40+0.4` and more rounds for a higher-confidence result once you've
got a candidate you actually want to trust before committing it.

## Part B: future parameter tuning

Deliberately not built yet — worth doing once most planned search/eval features have
landed and stopped changing shape, since tuned values from before a feature existed
(e.g. LMR reduction constants before check extensions are added) don't carry over well.
Two different tuning problems, two different tools:

- **Eval term weights** (material/PSQT/pawn-structure/mobility/king-safety tables in
  `eval.cpp`) — these are the natural target for **Texel tuning**: minimize prediction
  error of `evaluate()` against actual game outcomes over a large labeled position set,
  via local gradient descent/coordinate descent. No self-play games needed, so it's
  much cheaper per iteration than SPSA. `eval.cpp` already has a
  `load_eval_weights_from_file` stub waiting for this, and `tools/uci_eval` already has
  suite-scoring infrastructure that a labeled dataset + tuner could plug into.
- **Search-behavior constants** (RFP/razoring/futility margins, LMR formula constants,
  NMP reduction, aspiration window sizing) — these affect search dynamics, not just a
  static eval, so they need **SPSA tuned via self-play games**, not Texel. In practice
  this means running many short SPRT-style matches like the ones `run_sprt.ps1` already
  runs, perturbing one parameter (or a small correlated group) up/down each iteration
  and nudging it toward whichever direction wins more. Worth wiring as a wrapper around
  the same `fastchess` + book + worktree-build plumbing already in `run_sprt.ps1`, once
  there's a stable set of parameters worth tuning.
